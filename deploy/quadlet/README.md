# OpenTodo on one host, with podman quadlets

The same stack as [`../k8s`](../k8s) — OpenTodo behind HTTPS, with a Keycloak
realm brokering GitHub accounts into OpenTodo's OIDC sign-in — on a single
machine, as four systemd units generated by podman's quadlet.

Ansible does the work. The justfile is what you type.

```bash
cd deploy/quadlet
just init          # inventory.yml from the example
$EDITOR inventory.yml group_vars/all.yml
just vault-init    # generate the passwords, encrypt them
just vault-edit    # paste in your GitHub OAuth app credentials
just deploy
```

## Why both Ansible and just

They are not alternatives here, they are different jobs.

**Ansible** is the deployment: install podman, write the quadlet units, load
the podman secrets, render the Keycloak realm, open the firewall, start things
in the right order. It is idempotent, it runs against a remote host over ssh
or against `localhost`, and `just check` will show you what a run would change
before it changes it.

**just** is the interface: `just deploy`, `just logs keycloak`,
`just setup-token`, `just destroy`. Every recipe goes through the same
inventory, so they work the same whether the host is this machine or one
across the internet. Nothing in the justfile is load-bearing — delete it and
`ansible-playbook site.yml` still does everything.

Dependencies are deliberately thin: **ansible-core** on your machine (no
collections), **podman 5.0+** on the target. Quadlet arrived in podman 4.4,
but `Notify=healthy` — which is how Keycloak waits for its database — needs
5.0.

## What gets created

```
caddy.service              TLS, the only thing on :80 and :443
opentodo.service           the OpenTodo server, http on 8080
keycloak.service           Keycloak, http on 8080
keycloak-postgres.service  its database
```

on a private bridge network, with named volumes for the data and
`/etc/opentodo` for configuration. Only Caddy publishes a port.

```
deploy/quadlet/
  justfile                 the commands
  site.yml                 the playbook
  ansible.cfg
  inventory.example.yml    copy to inventory.yml
  group_vars/all.yml       hostnames, TLS mode, the knobs you change
  vault.example.yml        copy to vault.yml, fill in, encrypt
  roles/opentodo_stack/
    defaults/main.yml      every variable, with an explanation
    tasks/main.yml
    templates/             the four .container units, .network, .volume,
                           and the Caddyfile
```

## Caddy, and the three things that must agree

Caddy terminates TLS for both hostnames and is the only listener on the host.
It gets certificates from Let's Encrypt (`opentodo_tls_mode: acme`) or mints
them from its own CA (`internal`).

As in the Kubernetes deployment, three things have to line up:

1. **`OPENTODO_BASE_URL`** equals the address in the browser, exactly, or
   OpenTodo refuses sign-in with *"cross-site request rejected"*.
2. **`OPENTODO_OIDC_ISSUER`** equals the `issuer` field Keycloak publishes.
   It is derived from `opentodo_keycloak_host` rather than set separately,
   which is why there is no variable for it.
3. **The issuer URL resolves from inside the OpenTodo container.** OpenTodo is
   an OIDC *client*: it fetches the discovery document and exchanges the code
   for a token itself. Here that is handled by giving Caddy a fixed address on
   the podman network and pointing OpenTodo's `/etc/hosts` at it:

   ```
   AddHost=keycloak.example.com:10.89.70.10
   ```

   That keeps the call inside podman instead of hairpinning out to the host's
   public address and back, which NAT usually breaks.

The proxy headers are set differently for the two backends, on purpose:

| | |
|---|---|
| OpenTodo | Caddy **appends** to `X-Forwarded-For`, which is what OpenTodo documents wanting — it trusts private-range proxies and then takes the nearest untrusted hop |
| Keycloak | Caddy **replaces** `X-Forwarded-For`, because Keycloak's guide says the proxy must overwrite rather than append, and `KC_PROXY_HEADERS=xforwarded` reads the first entry |

Keycloak is published on only the three path prefixes its own reverse-proxy
guide says to expose — `/realms/`, `/resources/`, `/.well-known/`. Everything
else, `/admin/` included, gets a 404 from Caddy and never reaches the
container.

## The GitHub bridge

Identical to the Kubernetes deployment, because it is literally the same file:
the realm is rendered from `../k8s/base/keycloak/realm-template.json` by
`../k8s/base/keycloak/render-realm.sh`, which this role copies to the host and
runs. One realm definition, two deployments, no drift.

The setting that makes it work is `"trustEmail": true` on the GitHub provider.
OpenTodo refuses any identity whose ID token lacks `"email_verified": true`,
and Keycloak only emits that claim for a provider it has been told to trust.
[The Kubernetes README](../k8s/README.md#the-one-setting-the-bridge-turns-on)
explains what you are deciding when you turn it on.

Your GitHub OAuth app's callback URL is Keycloak's broker endpoint:

```
https://<opentodo_keycloak_host>/realms/opentodo/broker/github/endpoint
```

Leave `vault_github_client_id` empty and the realm is created with no identity
provider at all. The stack still runs; you sign in with Keycloak accounts.

## After the first deploy

1. **Create the OpenTodo owner** at `https://<opentodo_todo_host>`. The setup
   screen asks for a token, because the request arrives through Caddy rather
   than from loopback:

   ```bash
   just setup-token
   ```

   Do this promptly — until the owner exists, anyone with that token can claim
   the instance.

2. **Decide how people get accounts.** `OPENTODO_ALLOW_SIGNUP` is deliberately
   not set: it opens *password* registration as well as SSO provisioning, and
   setting it locks the panel field. Use *Settings → People → Single sign-on →
   Allow new accounts via SSO* instead.

3. **Link the owner, or do not.** Owners, admins, and any account with 2FA or
   a passkey are never linked to a brokered identity by matching email — they
   must link it from *Settings → Account → Security → Linked accounts*, or
   they see `oidc_link_required`. That is also your way back in if the
   provider breaks.

## TLS mode `internal`

For a host that is not on the public internet, or for a trial run.

Caddy runs its own CA and signs both hostnames with it. Two consequences:

- **Browsers need the root.** `just ca` fetches it to `./caddy-root.crt`.
- **So does OpenTodo**, because the discovery fetch above runs straight into
  it. The container mounts the root and sets `SSL_CERT_FILE`, which *replaces*
  the Go trust store rather than adding to it. That is why this mode also
  forces `OPENTODO_PUSH=off`: no other outbound https call would work. The
  role sets that for you.

Both hostnames still have to resolve to the host — through your own DNS, or
`/etc/hosts` on the machines you browse from.

## Changing things

| What | How |
|---|---|
| Hostname, TLS mode, images | `group_vars/all.yml`, then `just deploy` |
| A password | `just vault-edit`, then `just deploy` — the containers that read it restart |
| The PostgreSQL password | the same, **plus** an `ALTER ROLE keycloak PASSWORD …` inside the database. The container picks up the new value; the database does not. |
| OpenTodo's version | `opentodo_image` in `group_vars/all.yml`. It is pinned; `stable` moves with every release. |
| **The Keycloak realm** | **not by re-running the playbook** — see below |

### The realm, after the first start

`--import-realm` creates a realm that does not exist. **It never updates
one.** Re-rendering the import file changes nothing on a host that has already
started Keycloak once. This is the most surprising thing about the setup, so
the render task is marked `changed_when: false` and notifies nothing, rather
than pretending otherwise.

To change a redirect URI, the GitHub credentials, or the client secret on a
running host, edit the live realm:

```bash
just kcadm          # prints the command; it needs a tty, so run it on the host
```

[The Kubernetes README](../k8s/README.md#changing-the-realm-after-first-start)
has the `kcadm.sh` recipes — they are the same commands here.

## Operations

```bash
just status            # systemd state of all four units
just ps                # what podman thinks is running, with health
just logs keycloak     # journalctl for one unit
just restart opentodo
just down / just up    # stop and start, data kept
just destroy           # remove everything, including the data. Asks first.
```

- **Never run a second OpenTodo container.** One SQLite file, one writer.
- **Back up** `/etc/opentodo` (configuration, the realm import file, Caddy's
  certificates and CA) and the `opentodo-data` volume. Note that OpenTodo's
  own backups exclude `/data/secrets`, so the vault is what restores SSO.
- **Keycloak starts slowly**: `start` without `--optimized` augments the
  server on every boot, which is why its unit has a 10-minute start timeout.
  Build an optimized image with `kc.sh build` if that bothers you.
- **If the provider breaks** and SSO-only is on:
  `https://<host>/?owner=1` gives the owner a password form, and setting
  `OPENTODO_OIDC_SSO_ONLY=false` on the container is the documented override.
  The role leaves that variable unset so it stays available as the switch.

## How `tt` signs in

Unchanged by any of this. `tt` runs `ot`, and `ot` authenticates with an API
token, which keeps working under SSO-only. The one thing to know: an account
created through SSO has **no password**, so `ot login` with an email and
password is not available to it — create a token in the web interface and use
`ot auth set-token` or `OPENTODO_TOKEN`.

## What has been checked

Keeping with [`docs/opentodo-compatibility.md`](../../docs/opentodo-compatibility.md),
here is how far this has been verified:

| | |
|---|---|
| Quadlet units | Generated by podman 5.8.9's own `/usr/libexec/podman/quadlet -dryrun`, in both TLS modes, with no errors. The resulting `podman run` command lines were read and checked. |
| Playbook | `ansible-playbook --syntax-check` passes; every template renders in both TLS modes. |
| Realm renderer | Shared with the Kubernetes deployment and exercised there. |
| **End to end** | **Not run.** This has not been deployed to a host from this repository — no OpenTodo image has been started, no certificate issued, no GitHub sign-in completed. |

The open questions are the same ones [`../k8s/README.md`](../k8s/README.md#still-to-verify-against-a-live-cluster)
lists, plus two specific to this deployment:

1. That `/opentodo healthcheck` is the right exec probe for the image — it is
   what the image's own `HEALTHCHECK` is documented to run, but that is
   inference from the documentation rather than observation.
2. That Keycloak's bash/dev-tcp healthcheck works against its management port.
   Nothing depends on it; a wrong one shows up as a container stuck
   "unhealthy" while working fine.
